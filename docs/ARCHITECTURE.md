# Архитектура

## Задача

Есть несколько LAN-игр с общим сценарием: один экран, ведущий, гости с телефонами, комнаты, QR, живое состояние. Нужно:

- одна точка входа, чтобы не искать три разных проекта;
- независимые кодовые базы, чтобы агент работал в одной игре и не читал остальные;
- простая эксплуатация на Windows-ноутбуке в локальной сети;
- возможность добавлять новые игры без переписывания платформы.

## Решение

**Монорепо без workspaces. Несколько процессов. Тонкий портал. Фиксированные порты.**

```
                 ┌──────────────────────┐
   гость/экран → │  портал :8080        │  карточки, QR, статусы
                 └──────────┬───────────┘
                            │ обычные ссылки, без API-вызовов
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
 ┌────────────┐      ┌────────────┐      ┌────────────┐
 │ 100k :8101 │      │ svoy :8102 │      │ quiz :8103 │
 │ свой проект│      │ свой проект│      │ свой проект│
 └────────────┘      └────────────┘      └────────────┘
```

- Портал статичен для пользователя и имеет маленький Node-сервер для `games.json`, LAN-IP и проверки портов.
- Каждая игра — отдельный процесс со своим `package.json`, зависимостями, данными и `AGENTS.md`.
- Между играми нет вызовов, общей БД, общей авторизации и общего состояния. Связей ноль.
- Портал не импортирует код игр. Контракт — запись в `games.json` + URL + порт.
- Один лаунчер запускает всё, проверяет порты и останавливает процессы по `Ctrl+C`.

## Почему не другие варианты

### Один общий процесс / один `server.js`

Плохо: три разные механики, разные версии Express, CJS и ESM, разные WebSocket-библиотеки. Пришлось бы унифицировать всё ради экономии одного порта. Получился бы тот самый огромный контекст, которого нужно избежать.

### Path-прокси: `host/100k`, `host/svoy`

Красиво, но дорого в поддержке. У игр абсолютные пути `/js/...`, `/css/...`, `/sounds/...`, WebSocket на `/ws`, Socket.IO на `/socket.io/`, а QR строится от origin. При монтировании в подпуть ломается всё сразу. Каждая новая игра обязана быть «subpath-aware» с первого дня. Это постоянный налог и источник тонких багов.

### Поддомены: `100k.lan`, `svoy.lan`

Игры остаются в корне своего origin, правок почти нет. Но на LAN нужен DNS, который знает эти имена, а телефоны гостей — не всегда управляемые устройства. Лишняя точка отказа для вечеринки. Хороший вариант для VPS, не для локальной сети.

### Docker Compose

Полезен для воспроизводимости и поставки на Linux-сервер, но на Windows-ноутбуке добавляет проброс портов, тома, firewall и неработающий автооткрыв браузера. Изоляцию кода для ИИ Docker не даёт вообще: агент читает файлы, а не контейнеры. Поэтому Docker — возможный следующий слой, не фундамент.

### Слить игры в «движок»

Соблазнительно, но преждевременно. Общими могут стать комнаты, коды, таймеры, звук, загрузка паков. Но механики разные, и абстракция до четвёртой-пятой игры будет угадана неверно. Сначала дублирование, потом выделение.

## Границы и глубина

- **Игра** — глубокий модуль: снаружи видны только `npm start`, порт и URL. Внутри — сколько угодно сложности.
- **Портал** — тонкий слой: читает данные, рисует карточки, проверяет порт. Он не должен знать, как устроена игра.
- **`games.json`** — интерфейс между ними. Маленький, декларативный, без логики.
- **Процесс** — естественный шов. Он позволяет играм иметь разные зависимости, версии Node и стили кода, не заражая друг друга.

Главный тест границы: удалите портал — игры продолжат работать. Удалите игру — портал покажет на одну карточку меньше, код не сломается.

## Данные

- `questions/` — паки вопросов, лежат в игре.
- `data/` — история, состояние, локальные файлы, лежат в игре.
- Портал не читает данные игр.
- `data/` исключена из git; перед мероприятием делается резервная копия.
- Общей БД нет. Если появится общая статистика между играми, это будет отдельный сервис и отдельное решение.

## Отказы и диагностика

- Порт занят → лаунчер падает до запуска и перечисляет занятые порты. Никакого молчаливого автопоиска.
- Игра упала → остальные продолжают работать; портал показывает «не запущена».
- Портал упал → игры доступны напрямую по портам.
- Нет LAN-IP → QR и ссылки деградируют до `location.origin`; на localhost это ожидаемо.
- Нет интернета → всё работает: внешних CDN, шрифтов и API нет.

## Эксплуатация

- Node.js 22+.
- Windows Firewall: разрешить Node в частных сетях.
- Компьютеру желательно зарезервировать постоянный IP в роутере, иначе QR-ссылки меняются между запусками.
- Отключить сон на время мероприятия.
- Не пробрасывать порты в интернет. Авторизации нет.
- `start.bat` можно положить в автозагрузку, если платформа используется как киоск.

## Будущее

Порядок эволюции, если появится потребность:

1. **Один порт** — Caddy/nginx с path-прокси. Потребует привести ассеты к относительным путям, настроить `path` у Socket.IO и `ws`, добавить `PUBLIC_URL`. Делать только при реальной необходимости.
2. **Docker Compose** — по Dockerfile на приложение, порты наружу, тома для `data/`. Полезно для VPS и передачи проекта.
3. **`packages/`** — вынести LAN-IP/QR, коды комнат, таймеры, звук. Только после того, как дублирование доказано.
4. **Общая авторизация/профили** — отдельный сервис, не размазанный по играм.

Ни один из этих шагов не должен менять главное правило: игра остаётся самостоятельным проектом, а портал — тонким слоем.
