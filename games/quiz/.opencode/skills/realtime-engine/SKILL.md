# Realtime-движок Quiz Arena

## 1. Слоистость

```
HTTP / Socket.IO  →  тонкие адаптеры (валидация, авторизация, broadcast)
room-manager      →  комнаты, игроки, TTL, вход/выход, реконнект
GameEngine        →  чистая логика: createState / reduce / viewFor
shared            →  типы, события, Zod-схемы, форматтеры
```

Зависимости только `server → shared` и `web → shared`. Циклы запрещены.

```ts
interface GameEngine<S, A> {
  id: string;
  title: string;
  createState(cfg: RoomConfig): S;
  reduce(state: S, action: A, now: number): { state: S; effects: Effect[] };
  viewFor(state: S, viewer: Viewer): GameView;
}
```

`reduce` без I/O, без `Date.now()`, без `setTimeout`. Время — аргумент `now`. Это даёт детерминизм и лёгкие тесты.

## 2. Время и тайминги

- Источник — сервер: монотонные часы (`performance.now()`), не `Date.now()` для интервалов.
- Клиентское время не принимается и не влияет на порядок.
- `openBuzz`: `openedAt = now()`, очередь раунда очищается.
- Каждое нажатие: `seq` (порядковый номер поступления) и `deltaMs = clamp(now - openedAt, 0, …)`.
- Порядок — строго по `seq` (стабильно при равных миллисекундах).
- Отображение: лидер `0.00 с`, остальные `gap = t_i - t_leader` с точностью до сотых.
- `serverTime` кладётся в каждый snapshot; клиент рисует таймер от разницы серверного времени.

## 3. Очередь и вердикты

Инварианты:

- `buzz` только в `buzz_open`.
- Один игрок не может иметь две `waiting`-записи.
- Rate limit: не чаще 1 раза в 250 мс на игрока (спам игнорируется, не логируется как ответ).
- «Активен» первый `waiting` в очереди — ему админ ставит вердикт.

`verdict(correct=true)`:
- лидеру `+1`, статус `correct`, раунд → `round_result`;
- повторный вердикт по тому же `entryId` — no-op (идемпотентность).

`verdict(correct=false)`:
- статус `wrong`, запись уходит из активной очереди;
- игрок **может нажать снова** — новое нажатие = новая запись с новым `seq`/`deltaMs`;
- следующий `waiting` становится лидером, фаза остаётся `buzz_open`.

`closeBuzz` → `round_result` без очков (ноль нажатий или все ответили неверно).

`finish` → из любой фазы кроме `lobby`, сохраняет матч, → `finished`. Повторный вызов не создаёт дубль.

## 4. Очки и рейтинг

- Верно = ровно +1 (`speedBonus: false`).
- Сортировка: очки ↓ → верных ответов ↓ → суммарное время верных нажатий ↑ → иначе ничья (одинаковый rank, «ничья»).
- В историю пишутся все игроки с `rank`, а победителей может быть несколько (ничья).

## 5. Socket.IO слой

Ack-контракт для всех клиентских вызовов:

```ts
type Ack<T> = { ok: true; data: T } | { ok: false; error: { code: ErrorCode; message: string } };
```

Коды: `FORBIDDEN`, `ROOM_NOT_FOUND`, `NICK_TAKEN`, `INVALID_STATE`, `VALIDATION`, `RATE_LIMITED`, `ROOM_FULL`.

Правила:

- Каждый входящий payload проходит Zod-схему из `src/shared/schemas.ts`; ошибка → `VALIDATION`.
- Единый обработчик ошибок на сокет, логирование через pino.
- `adminKey` проверяется на сервере для каждого админ-события, иначе `FORBIDDEN`.
- `playerToken` — `crypto.randomUUID()`; `adminKey` — 32 байта hex.
- При реконнекте сервер сразу отдаёт `state:snapshot`; клиент полностью перерисовывается.
- `viewFor(state, viewer)` скрывает текст вопроса от игроков, если `showQuestionOnPlayerDevices: false`.
- Broadcast: `players:updated` при изменении состава/очков, `queue:updated` после каждого нажатия и вердикта.
- Комнаты в памяти; TTL по `roomIdleTimeoutMin`, grace админа `adminReconnectGraceMin`.

## 6. Крайние случаи (проверять тестами)

| Случай | Поведение |
|---|---|
| Игрок обновил страницу / потерял Wi-Fi | реконнект по `playerToken` ≤ 90 с, место в очереди и очки сохраняются |
| Позже 90 с | новый вход с 0 очков (или зритель) |
| Админ обновил страницу | `adminKey` из localStorage восстанавливает права |
| Поздний вход в игре | 0 очков, участвует со следующего раунда |
| Ноль нажатий | `closeBuzz` без очков |
| Все ответили неверно | админ вручную `nextQuestion` |
| Падение сервера | комнаты теряются (MVP), незавершённый матч не пишется, описать в README |
| Одновременное нажатие в одну мс | порядок по `seq`, gap `0.00`/`0.01` |
| Завершение при открытом приёме | принять, сохранить только завершённые раунды |
| Вердикт дважды | второй игнорируется |
| Игрок жмёт «Верно/Неверно» | `FORBIDDEN` |
| Ники-дубли/пробелы/HTML/XSS | trim, 2–20, case-insensitive уникальность, React-экранирование |

## 7. Тесты

**Unit (Vitest, fake clock, без реальных таймеров):**

- переходы фаз и запрет недопустимых действий;
- порядок очереди и `seq`, `deltaMs`, клампинг отрицательных;
- `correct → +1` и `round_result`;
- `wrong → конец очереди + можно нажать снова`, лидер меняется;
- rate limit 250 мс и запрет двух `waiting`;
- идемпотентность `finish` и повторного вердикта;
- определение победителя и все тай-брейки;
- Zod-валидация payload'ов.

**Integration (Vitest):**

- сервер на эфемерном порту + 3–4 клиента `socket.io-client`;
- полный сценарий: create → join ×N → start → openBuzz → buzz с задержками → verdict → nextQuestion → finish;
- проверка прав без `adminKey` → `FORBIDDEN`;
- реконнект и получение snapshot.

## 8. Частые ошибки

- ❌ Считать очки/порядок на клиенте или по клиентскому времени.
- ❌ `Date.now()` внутри `reduce` — ломает тесты и детерминизм.
- ❌ Мутировать состояние in-place вместо нового объекта.
- ❌ Отправлять клиентам текст вопроса, когда флаг выключен.
- ❌ «Догонять» пропущенные события вместо snapshot.
- ❌ Хранить очередь в нескольких местах (state + отдельная Map) — рассинхрон.
- ❌ Логировать каждое нажатие в БД — только в лог-файл.
