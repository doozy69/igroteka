# Решения и компромиссы

## 1. Ванильный фронтенд без сборки

HTML + CSS + ES-модули вместо React/TypeScript. Проект запускается одной командой `node server/index.js`,
не требует Vite и не скачивает зависимости в браузере. Цена — ручной рендер через `replaceChildren` и
небольшой самописный `el()` в `public/js/dom.js`. Для одного экрана комнаты и пяти фаз этого достаточно.

## 2. Одно событие `state` — полный срез

Любое изменение комнаты рассылается как полный публичный срез (`game.toPublic`). Клиент ничего не
вычисляет и не хранит очередь — только рисует. Это исключает рассинхрон после реконнекта и убирает
целый класс багов «событие потерялось». Трафик при 12 игроках и нескольких нажатиях ничтожен для LAN.

## 3. Серверное время — единственный источник истины

Порядок нажатий и `deltaMs` считаются на сервере через монотонные `performance.now()`. Клиент не
отправляет время нажатия. Для отображения таймера сервер кладёт `openedAt` (epoch) и `serverTime`;
клиент считает смещение `serverTime - Date.now()` и рисует часы от него. Часы телефона могут врать —
на порядок в очереди это не влияет.

## 4. JSON-файл вместо SQLite

История — `data/history.json`, запись атомарная (`.tmp` + `rename`), записи сериализуются промисом,
лимит 200 матчей, дедупликация по `id`. Удаление файла — понятный способ очистить архив, без миграций
и клиентов БД. Минус — вся история в памяти; для домашней викторины это несущественно.

## 5. Идентификация без аккаунтов

Игрок — `playerId` (`crypto.randomUUID()`) в `localStorage`. Ведущий — дополнительно `adminKey`
в `localStorage` под ключом `quiz:admin:<code>`. Никаких паролей и регистрации. Перезагрузка страницы
возвращает игрока в комнату с теми же очками; чужой браузер ведущим не станет.

Важная деталь: `crypto.randomUUID()` работает только в secure context (localhost или HTTPS). При игре
по `http://192.168.x.x` браузер его не даёт, поэтому `public/js/socket.js` генерирует UUID вручную из
`crypto.getRandomValues`. Без этого телефоны в LAN не могли войти в комнату.

## 6. Очередь нажатий вместо «первого победителя»

Каждое нажатие создаёт запись в очереди с `seq` и `deltaMs`. Вердикт «неверно» помечает запись и
передаёт лидерство следующему, «верно» — начисляет очко и завершает раунд. Так ведущий может принять
несколько неверных ответов, не переоткрывая приём. Повторное нажатие из очереди запрещено, после
неверного ответа игрок в этом раунде больше не нажимает — иначе один и тот же человек мог бы
«перехватывать» ход бесконечно. Есть антиспам 150 мс на игрока.

## 7. Текст вопроса виден всем

Ведущий читает вопрос вслух, поэтому скрывать текст на клиентах бессмысленно. Публичный срез содержит
`question`; поле в панели ведущего синхронизируется у всех. Это зафиксировано как осознанное упрощение,
а не утечка.

## 8. Ники уникальны, вход после старта разрешён

Два одинаковых ника в комнате невозможны: сервер отвечает `NICK_TAKEN` и предлагает вариант с цифрой.
Игрок может присоединиться в любой момент до завершения игры — он получит 0 очков и будет виден в
таблице. Повторный вход с тем же `playerId` считается реконнектом, а не новым игроком.

## 9. Матч сохраняется ровно один раз

История пишется в момент `finish`. Флаг `room.saved` и `room.matchId` делают повторное нажатие
идемпотентным: матч не дублируется, а клиент получает тот же `matchId`. Пока игра не завершена,
`/history` пуст — это ожидаемо.

## 10. Ранжирование с тай-брейками

Сортировка: очки → число верных ответов → суммарное время верных ответов → ник. Равные по всем
показателям делят место (1, 2, 2, 4). Победа — все игроки с рангом 1; в истории сохраняется массив
`winners`, поэтому ничья не теряется.

## 11. Что сознательно отложено (P1)

QR-код, звуки, CSV, portable Node.js и ZIP, отдельная полировка ТВ, RTT-компенсация, дополнительные
вопросы для тай-брейка. В MVP их нет, чтобы не усложнять игровое ядро и запуск. ТВ-табло при этом
работает как режим только для чтения (`/r/:code/tv`) и не влияет на игру.
