# Промт для разработки веб-игры «100 к одному» (Node.js + WebSocket, без БД)

## Роль
Ты — senior full-stack разработчик. Разработай полностью рабочий веб-проект — командную игру «100 к одному» (аналог телеигры *Family Feud* / «Сто к одному») на **Node.js** с **WebSocket** в реальном времени.  
Проект должен работать **без базы данных**: все вопросы, раунды, настройки и (опционально) пресеты игр хранятся в **JSON-файлах**. Состояние текущей игры хранится в памяти сервера.

## Цель
Сделать готовое к запуску приложение с тремя интерфейсами:
1. **Админ-панель (ведущий/оператор)** — управление игрой, раундами, командами, очками, показом ответов.
2. **Экран ТВ/табло (display)** — публичный экран для вывода на большой монитор/проектор/телевизор (зрелищный интерфейс).
3. **Мобильный интерфейс игроков** — вход по коду/ссылке, выбор команды (или назначение), ввод ответов, участие в розыгрышах и «Большой игре».

Сервер синхронизирует все экраны в реальном времени через WebSocket.

## Технологический стек (на твой выбор, но в рамках требований)
Обязательно:
- **Backend:** Node.js
- **Realtime:** `ws` (или совместимая обёртка, но предпочтительно нативный `ws`)
- **Хранилище:** только JSON-файлы на диске + in-memory state (без SQLite/Postgres/Mongo/Redis)

Рекомендуется (можно выбрать аналог):
- HTTP-сервер/роутинг: Express / Fastify / нативный `http`
- Frontend: React / Vue / Svelte / или чистый HTML+CSS+Vanilla JS (выбери простой и надёжный вариант)
- Сборка (если нужна): Vite
- Валидация: `zod`/`ajv` или своя валидация
- Стили: CSS modules/Tailwind/обычный CSS — на твой выбор, но UI должен быть аккуратным и адаптивным

Требование: проект должен запускаться локально простыми командами (`npm install`, `npm run dev` / `npm start`) и иметь понятный `README.md`.

- подключённые клиенты по ролям (`admin`, `display`, `player`) и сессиям

Обеспечь восстановление UI при переподключении клиента (сервер отправляет полный snapshot состояния).

## Роли, интерфейсы и маршруты

Сделай отдельные экраны/маршруты (пример):
- `/admin` — админ-панель (защита паролем/токеном из `settings.json` или простая авторизация)
- `/display` или `/tv` — экран табло для телевизора
- `/` или `/play` — мобильный вход игрока (код игры/комнаты)
- `/play/:gameCode` — мобильный интерфейс игрока в конкретной игре

### A. Админ-панель (ведущий)
Должна позволять:
- Создать/выбрать игру из JSON-пакета, сгенерировать код комнаты
- Назначить/переименовать 2 команды, добавить игроков (или принять подключения), выбрать капитанов
- Запускать/переключать раунды и вопросы
- Управлять ходом раунда: начать розыгрыш, выбрать победителя розыгрыша, передать ход
- Открывать правильные ответы на табло (вручную по клику и/или автосопоставление по введённому ответу)
- Засчитывать промах (страйк), снимать страйк при ошибке (undo)
- Запускать блиц-опрос при 3 страйках и выбирать версию капитана
- Управлять «Игрой наоборот» (сбор ответов команд, раскрытие, начисление очков)
- Управлять «Большой игрой» (выбор 2 игроков, таймеры 20/25 сек или настраиваемо, ввод/фиксация ответов, подсчёт, reveal)
- Показать/скрыть табло-элементы, проиграть звук промаха/успеха (опционально)
- Вручную корректировать очки/фонд/состояние (на случай спорных ситуаций)
- Сбросить раунд/игру, экспортировать итог в JSON-файл (опционально, без БД)

UI админа — функциональный, с явным отображением текущего состояния, кнопками действий и логом событий раунда.

### B. Экран ТВ/табло (Display)
Публичный зрелищный экран:
- Крупные названия команд и счёт
- Текущее название раунда и вопрос (когда нужно показывать)
- Табло из 6 строк: скрытые/открытые ответы, очки за ответ
- Фонд раунда (сумма открытых очков)
- Индикаторы промахов (X) по активной команде/контексту
- Анимации открытия ответов, страйков, начисления очков
- Режимы для «Игры наоборот» и «Большой игры» (отдельная верстка/панели)
- Экран ожидания/лобби с кодом подключения и QR-кодом (опционально)

Важно: Display **не** должен показывать скрытую служебную информацию (неоткрытые ответы, ответы первого игрока в «Большой игре» до reveal и т.п.), если админ это не разрешил.

### C. Мобильный интерфейс игроков
- Подключение по коду комнаты (и/или ссылке/QR)
- Ввод имени, выбор команды (или ожидание назначения админом)
- Отображение статуса: ожидание, ваш ход, вы отвечаете в розыгрыше, большая игра и т.д.
- Отправка ответа (текстовое поле + кнопка) в нужные моменты
- В «розыгрыше» — быстрая отправка ответа (и опционально кнопка «Я первый» если решишь реализовать так; лучше фиксировать порядок на сервере по времени получения)
- В «Игре наоборот» — отправка одной финальной версии от команды/капитана (по правилам выбранной реализации)
- В «Большой игре» — экран для выбранного игрока с таймером и 5 вопросами/поочерёдным вводом

Мобильный UI должен быть адаптивным, с крупными кнопками и понятными состояниями.

## Правила игры (реализовать логику)

Ориентируйся на правила «Сто к одному» (Wikipedia) и дополни здравой логикой для интерактивной веб-версии.

### Общие принципы
- Играют 2 команды по 5 человек (допусти настраиваемое число игроков, по умолчанию 5).
- На табло 6 самых популярных ответов с количеством очков (число людей из опроса).
- Очки открытых ответов идут в фонд раунда, затем победителю розыгрыша раунда/команде по правилам.
- Промахи отображаются как X/страйки.

### Раунды
1. **Простая игра**
   - Розыгрыш между игроками (обычно капитаны/первые номера): ведущий зачитывает вопрос, игроки дают версии, определяется команда, продолжающая раунд.
   - Команда по очереди называет ответы, пока не откроет все 6 строк или не получит 3 промаха.
   - При 3 промахах — блиц-опрос другой команды, капитан выбирает одну версию; если она есть на табло — очки фонда уходят этой команде, иначе — команде, игравшей раунд.

2. **Двойная игра**
   - То же, что простая, но очки за открытые ответы ×2.
   - Розыгрыш обычно между следующими игроками команд.

3. **Тройная игра**
   - То же, что простая, но очки за открытые ответы ×3.
   - Розыгрыш между следующими игроками команд.

4. **Игра наоборот**
   - Цель — угадать непопулярный ответ (низ на табло), за него даётся больше очков.
   - Команды совещаются (таймер ~20 сек), капитаны дают по одной финальной версии.
   - Очки начисляются по таблице редкости (например 15/30/60/120/180/240 за 1–6 строки) — сделай таблицу настраиваемой в JSON.
   - Если счёт после раунда равный — предусмотри тай-брейк (например, доп. вопрос или ручное решение админа).

5. **Большая игра (финал)**
   - Играют 2 игрока победившей команды.
   - Игрок 1 отвечает на 5 вопросов за ограниченное время (настраиваемо, напр. 15 сек). Его ответы и очки скрыты от игрока 2.
   - Игрок 2 отвечает на те же 5 вопросов (напр. 20 сек). Нельзя повторять ответы игрока 1 (при совпадении — запросить другую версию/пометить дубликат).
   - Очки за совпадения с популярными ответами суммируются. Если сумма ≥ порога (обычно 200, сделать настраиваемым) — команда выигрывает суперприз/финал.

### Уточнения реализации (важно)
- **Сопоставление ответов**: реализуй нормализацию (регистр, пробелы, ё/е, простая пунктуация) и поддержку `aliases` из JSON. Админ должен иметь возможность вручную подтвердить/открыть нужную строку, если авто-матч не сработал.
- **Один ответ — одна строка**: нельзя дважды открыть ту же строку.
- **Порядок ответов игроков в розыгрыше**: определяй сервером по времени прихода события, чтобы избежать споров.
- **Undo/ручное управление**: ведущий в TV-шоу часто принимает решения вручную — админ-панель должна позволять исправлять ошибки оператора.
- **Гибкость**: сделай количество раундов/вопросов конфигурируемым через JSON-сценарий игры.

## Архитектура и WebSocket-протокол

### Компоненты
- HTTP сервер раздаёт статику/страницы и JSON-конфиги (только то, что безопасно для клиента)
- WS-сервер управляет комнатами/игрой и рассылает события
- Единый источник истины состояния — на сервере

### Рекомендуемая модель сообщений (JSON)
Используй единый формат, например:
```json
{ "type": "ACTION_NAME", "payload": { } }
```
И события от сервера:
```json
{ "type": "STATE_SNAPSHOT", "payload": { } }
{ "type": "EVENT", "payload": { "name": "ANSWER_REVEALED", "data": { } } }
{ "type": "ERROR", "payload": { "message": "..." } }
```

### Примеры действий клиента → сервер
- `JOIN_SESSION` `{ role: "admin|display|player", gameCode, token?, name?, teamId? }`
- `ADMIN_CREATE_GAME` / `ADMIN_LOAD_PACK` / `ADMIN_START_ROUND`
- `ADMIN_FACE_OFF_START` / `ADMIN_SET_ACTIVE_TEAM` / `ADMIN_REVEAL_ANSWER` / `ADMIN_ADD_STRIKE` / `ADMIN_ASSIGN_POINTS`
- `PLAYER_SUBMIT_ANSWER` `{ text }`
- `PLAYER_BIG_GAME_ANSWER` `{ questionIndex, text }`
- `ADMIN_NEXT_PHASE` / `ADMIN_UNDO` / `ADMIN_FINISH_GAME`

### Примеры событий сервер → клиенты
- `STATE_SNAPSHOT` (полное состояние для роли/экрана; фильтруй данные по роли!)
- `ANSWER_REVEALED`, `STRIKE_ADDED`, `ROUND_FUNDS_UPDATED`, `TEAM_SCORES_UPDATED`
- `TIMER_TICK`, `PHASE_CHANGED`, `PLAYER_JOINED/LEFT`
- `BIG_GAME_REVEAL_PROGRESS`

### Требования к синхронизации
- Все критические изменения состояния проходят через сервер
- При переподключении клиент запрашивает/получает актуальный `STATE_SNAPSHOT`
- Разграничивай данные по ролям (Display и Player не получают скрытые ответы/служебные поля)
- Обрабатывай отключения, повторные подключения и некорректные сообщения без падения сервера
